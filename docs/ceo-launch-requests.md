# Recalls Tutor — CEO decisions and launch inputs

Prepared 9 November 2026. This is a launch checklist, not a declaration that the PRD or QA is complete. Vercel project and environment settings have not yet been verified because the connected team denied access pending the user's approval.

## Decisions and access needed

- **Business and billing:** legal entity receiving revenue; authorised Stripe account owner and access; Stripe test and live configuration; approved USD prices for each 3-, 6- and 12-month plan per launch exam; confirmation of any monthly plan, bundles, renewal and cancellation terms; VAT/GST/Stripe Tax decisions with an accountant; final refund policy and coupon rules.
- **Content:** which exam launches first (MRCOG Part 1 is only a working assumption); minimum approved question count; authorised source recalls and permission to use them; named reviewers and final approval owners; real exam blueprint, paper count, duration, topic weights and official pass mark where published. Confirm trial pool excludes the latest diet.
- **Legal and privacy:** counsel's review of exam recall sourcing and candidate confidentiality, terms, privacy notice, refund policy, processor agreements and retention/deletion rules. New local image OCR does not send the original image to a provider; its deployment and handling still need verification. Text redaction is not guaranteed to catch every identifier.
- **AI providers:** choose and approve actual model IDs, data handling, region and paid usage budgets; provide credentials through Vercel secret settings, not chat. The user has approved Anthropic, OpenAI, Gemini and Groq as possible text providers. The fallback supports up to five configured entries across them; each needs credentials, quota and quality evaluation. Local non-LLM OCR handles images and scanned PDFs, with a 20-page PDF cap; the deployed runtime and OCR accuracy on real samples require verification.
- **Infrastructure:** Vercel team/project access and production URL; domain/DNS; hosted PostgreSQL with backups and restore ownership; verified transactional email sender; initial administrator and support contacts; monitoring/incident owner. Confirm production secrets and scheduled jobs are configured without sharing their values in chat.
- **GitHub and GoHighLevel:** The user requested on 11 November 2026 that GitHub and GoHighLevel integration be included in the handoff for Claude. Confirm the intended GitHub workflow and GoHighLevel account, integration requirements, credentials, consent and launch priority before implementation. This supersedes the earlier exclusion of GoHighLevel.

## Engineering and QA gates still open

- Verify the actual Vercel deployment, active commit, configured environment names, database migrations, domains and cron execution. A successful deployment alone is not full production readiness.
- Run end-to-end signup → email verification → trial → Stripe test checkout → entitlement → practice → cancellation/renewal. Test declined payments, seven-day grace, refunds, disputes, out-of-order/replayed webhooks and reconciliation with Stripe test clocks before live payments. Local simulated tests cover billing workflows and active/expired webhook claims; they do not replace Stripe test-mode verification or prove exactly-once side effects after a worker crash.
- On 10 November, local configuration had no Stripe secret or webhook secret, so a real test checkout could not be run. Local adapter tests now also reject malformed successful responses when creating products, prices, customers or checkout sessions; this is not Stripe test-mode verification.
- **Checkout coordination needs production verification:** a per-student/per-exam reservation now reuses an open checkout, preserves the Stripe idempotency key after a lost response, blocks new checkouts while payment is processing, and replaces an expired session. A new purchase can start after Stripe and the local record both confirm cancellation. Local simulated tests cover those cases and overlapping requests using the embedded database. Real Stripe test-mode and independent-connection PostgreSQL tests are still required, including delayed payments, crash recovery and monitoring; an unconfirmed reservation older than 23 hours requires support rather than risking another charge. The implementation holds a database row lock during Stripe calls; calls have a 15-second timeout, but latency and failure recovery still need production-like testing. Account-wide duplicate-subscription settings need care because students may buy access to different exams.
- Validate 3/6/12-month price mapping and user-facing renewal disclosures against approved Stripe products. Configure real webhook and Customer Portal only when authorised.
- Evaluate each AI model against reviewer-approved examples, including answer/reference accuracy, unsafe instructions and failover; confirm only humans can publish. A provider quota failover can generate additional cost and does not imply interchangeable medical quality.
- Original PRD asks for semantic deduplication with automatic high-confidence merges. An opt-in implementation links evidence and sitting tags without creating another question; published content changes remain proposals for human approval. It is disabled by default: the embedding model and threshold must be calibrated against labeled medical recall pairs and broader concurrency coverage verified before production use. Reviewers can also compare, keep both, merge a draft or propose a replacement. Studio jobs reject a stale comparison when another job changes the bank. Embeddings are recomputed for the full bank per job; this needs caching and scaling work before production. Enabling semantic matching sends question stems to OpenAI; approve the model, data handling and budget first. The paper editor, proposals and an optional full-size timed random set use configured question counts, type counts and top-level topic counts. Publication and student paper access recheck the blueprint, and new verified attempts record it for the predictor; older attempts have no verified snapshot and do not count toward its complete-paper requirement. Existing questions require human type classification and the exam team must enter real targets. Non-single-answer question formats remain unsupported in the student flow.
- Original PRD calls for up to 500 MB per upload batch; current implementation has a 4 MB aggregate limit. HEIC photos are processed locally and have passed a synthetic local test; production deployment and broader device compatibility still need verification. XLSX cell values and text chat exports inside ZIP archives are accepted, subject to extraction and job text limits. A separate CSV/XLSX clean-question import validates rows and creates drafts only, with local permission, atomicity and retry tests. It rejects exact matches and, when embeddings are configured, possible semantic matches against the bank or within the file; staff must compare and revise the file. Local Chrome checks covered a CSV validation error and correction, and an XLSX import and duplicate warning at 390px width; production and broader device verification remain outstanding. A scheduled recovery path restarts older queued or stalled sanitized text jobs and fences out an earlier worker, but scans are not retained and provider requests made before a retry can still incur cost. This is not yet a proven durable queue for large files. Confirm the hosting plan supports the configured cron frequency.
- Text-only uploads above the single-job limit are now cleaned as a whole and atomically split into queued jobs, up to 4 MB of cleaned text; local tests cover splitting, cleaning and idempotent retry. The first job starts immediately and the existing scheduled recovery handles the rest one at a time, so large batches can be slow and depend on cron. Mixed scans and text still use the single-job path. Completing the 500 MB path still requires private direct-to-storage uploads, authorization and batch accounting, durable large-file processing, cross-boundary PII handling, retention/deletion, retry recovery, format-specific extraction and load tests. A private storage service and retention policy must be configured before the full path can be verified.
- Duplicate comparison now coordinates with staff edits, review decisions, AI refinements and accepted proposals by exam; a local test verifies an import rejects a comparison made stale by an edit. A separate test confirms a review decision made during AI refinement is not overwritten. These focused tests do not replace multi-worker production database concurrency and load testing.
- Local paper tests verify that a previously published paper is hidden and cannot be started if a question is retired, its type or topic changes, or the exam's configured topic targets change. Real exam blueprints, non-SBA formats and production concurrency still need verification.
- Student practice currently renders single-best-answer questions only. Explicitly classified EMQ, MCQ and true/false questions are now excluded, and complete papers containing them are hidden and blocked from starting. Unclassified legacy questions are treated as SBA because the existing editor creates five-option single-answer drafts; they still require classification for blueprint validation. Implement the missing formats and verify legacy content before launch.
- If a question is reclassified to an unsupported format after a session, results and history exclude it from scoring, and the core predictor and progress dashboard exclude it from their supported-question inputs. Local tests cover results, history and progress recalculation; broader reporting consistency and predictor regression on real content remain QA work.
- Confirm mobile/browser accessibility, paid-content isolation, rate limiting, MFA, session/device restrictions, backups/restore, p95 load and exam-week load tests. Question-type filtering is implemented for classified questions; image filtering and full support for non-single-answer formats remain outstanding. Record actual results. Verify emails, monitoring and consent before accepting students.
- The prior checkpoint lists bundles, subscription pause, Stripe Tax, web push and SSO as not built. Those are later-phase or business-dependent; do not claim the complete app is finished. Confirm the desired release scope and other original-PRD phase differences.

## Current verification

On 10 November, an earlier run of 67 local automated tests passed, including simulated billing and provider tests, semantic merging, human publication permissions, clean-question import and synthetic HEIC OCR. The later text batching change passed focused tests and TypeScript, but has not had a full suite or production build. These checks do not replace live integrations or browser and load QA. The text fallback is not yet configured in Vercel, tested with real paid provider credentials, or deployed. Local OCR also passed synthetic image, scanned-PDF and mixed-page PDF tests; a page with substantial selectable text over a separate image may still omit image-only content. An earlier isolated Windows production build succeeded; its Studio trace includes the HEIC decoder, OCR engine and language data. The Linux/Vercel package and deployed-runtime behavior remain unverified. Provider-specific cost accounting remains outstanding. Full current production integration and release QA have not been signed off.
