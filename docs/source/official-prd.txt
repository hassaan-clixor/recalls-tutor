Recalls Tutor — Product Requirements Document
Oct 28, 2026 · @Someone
1. Overview
Recalls Tutor is a responsive web platform that sells exam recall question banks, refined by an AI Recall Studio and sold per exam sitting through Stripe in USD. There is no native mobile app; every screen must work fully in a mobile browser.
Vision: become the go-to recall QBank for postgraduate medical licensing exams. Students buy access for their exam date, practise in Exam and Revision modes, sit complete mock papers, and pass.
Business goals
• Turn raw, messy recall dumps (WhatsApp exports, PDFs, Word files, screenshots) into a clean, tagged, exam-ready QBank with minimal manual effort.
• Sell simple 3, 6 and 12-month plans per exam that renew automatically.
• Rank organically for recall-related searches per exam (e.g. "MRCOG Part 1 recalls September 2026").
• Keep the QBank fresh by adding each new exam diet's recalls soon after the exam.
In scope (v1)
1. SEO marketing website (public).
2. Student portal (signup, purchase, practice, renewals, analytics).
3. Admin portal (QBank, plans, users, billing, reports).
4. Recall AI Studio (ingest, refine, dedupe, tag, review, publish).
5. Subscription plans (3, 6 and 12 months per exam).
6. Stripe USD billing.
Launch exams: MRCOG Part 1, MRCOG Part 2 and AMC Part 1. The data model must support any exam family (PLAB, MRCP, FCPS, USMLE etc.) with no code changes. Many exam recalls will be added over time, so exams, tags, blueprints, style profiles, SEO pages and plans are all created from admin, never hard-coded.
Out of scope (v1): native iOS/Android apps, offline mode, live tutoring, multi-currency pricing.

4. Recall AI Studio
The Studio turns any pile of poor-quality recalls into publish-ready questions: the team dumps files in, the Recall AI Agent extracts, refines, de-duplicates and tags them, and a human reviewer approves. Target: under 5 minutes of human time per published question.
Raw files flow through AI extraction, refinement and de-duplication, then stop at human review; student error reports re-enter at the same review step.
4.1 Ingestion ("dump zone")
• Drag-and-drop bulk upload, up to 500 MB per batch.
• Supported inputs: PDF (text and scanned), DOCX, XLSX/CSV, TXT, WhatsApp/Telegram chat exports (.txt/.zip), images (JPG/PNG/HEIC screenshots), and pasted text.
• On upload the user sets optional hints: exam, sitting, source name. The agent infers anything missing and flags low confidence.
• OCR for scans and screenshots, including handwritten notes where legible.
• Each upload becomes a Job with live status: Queued → Extracting → Refining → Deduping → Ready for review.
4.2 Extraction
• Split raw text into individual recall fragments (a fragment may be one line like "Q about nerve supply to levator ani").
• Separate stems, partial options, student guesses, and chat noise (greetings, emojis, off-topic messages are discarded).
• Pull out images and attach them to the right fragment.
• Capture student-claimed answers and discussion as evidence, not as truth.
4.3 Refinement (per fragment)
The agent produces a complete, exam-style question:
1. Reconstructed stem in the real exam's style and length (e.g. MRCOG SBA clinical vignette).
2. Options: completes to the exam's format (A–E for SBA, theme + option list for EMQ) with plausible, evidence-based distractors.
3. Correct answer with a confidence score (0–100). Below a threshold (default 80) the question is flagged for expert attention.
4. Explanation: why the right answer is right and why each distractor is wrong.
5. Key learning notes: 3–5 bullet revision points.
6. References: guideline or textbook source (RCOG Green-top, NICE, eTG, standard texts) — the agent must cite only real sources and the reviewer verifies them.
7. Taxonomy: exam, topic, sub-topic, difficulty, question type.
8. Image handling: keep, clean up or flag images; suggest a placeholder description when an image is referenced but missing.
Each exam has an editable Exam Style Profile (prompt template, option count, stem length, guideline sources, tone) so output matches that exam.

4.4 De-duplication and attempt tagging
• Semantic similarity check (embeddings) against the full QBank and the current batch.
• Match above the high threshold → merge: no new question; add the new sitting as an Attempt Tag and attach the new upload as extra evidence.
• Possible match (middle band) → reviewer sees both side by side and picks Merge, Keep both, or Replace.
• Different recalls of the same question improve it: the agent proposes edits when new evidence adds detail (e.g. a missing option).
• Each Attempt Tag stores how many independent sources recalled it, which feeds the High-yield badge.
4.5 Review workflow
• Review queue sorted by confidence (lowest first), filterable by exam, sitting, topic, reviewer.
• Side-by-side view: raw source evidence on the left, refined question on the right, with inline editing.
• Actions: Approve, Edit and approve, Send back to AI with instructions ("make distractors harder"), Reject, Merge.
• Optional two-step approval for an exam (Reviewer, then Content Manager).
• Every change logged with who, when and what.
• Bulk actions for high-confidence questions (approve 20 at once after a skim).
4.6 Paper builder
• Agent proposes Complete Papers for a sitting that match the Exam blueprint (question count, type mix, topic weighting).
• Content Manager can drag to reorder, swap questions, and lock a paper.
• Papers labelled e.g. "MRCOG Part 1 — Sep 2026 Recall Paper 1".
4.7 Student feedback loop
• Students can report a question (wrong answer, unclear, typo, image missing).
• Reports return to the review queue with the student's note; the agent drafts a fix.
• Questions with high error rates in practice are auto-flagged for a quality check.
4.8 AI guardrails
• Agent never publishes; humans do.
• Confidence and "needs expert" flags are mandatory on every AI output.
• References must be verifiable; unverifiable claims are flagged.
• Raw sources and student identities from chat exports are never shown publicly, and personal data in uploads (names, phone numbers) is stripped on ingestion.
• Usage and cost per job tracked in admin.

6.9 Pass Predictor
The Pass Predictor tells each student how likely they are to pass on their exam date and what to fix. It unlocks after one complete Exam Mode paper and at least 300 answered questions.
Output shown to the student
• Pass likelihood band: Low / Borderline / Likely / Very likely, with a predicted score range against the pass mark (where the exam body publishes one).
• Trend line: how the prediction has moved over the last 4 weeks.
• "What would move you up": the 3 topics and subtopics with the biggest gain per hour of study.
• Days left and the daily question target needed to reach "Likely" before the exam.

7. Billing (Stripe, USD)
Billing uses Stripe Subscriptions in USD: each exam has 3, 6 and 12-month recurring prices that auto-renew until the student cancels (section 5).
7.1 Stripe setup
• Currency: USD only.
• One Stripe Product per Exam with three recurring Prices (every 3, 6 and 12 months); price changes create a new Price and existing subscribers keep their old price unless migrated.
• Stripe Checkout (hosted) for payment — handles cards, Apple Pay, Google Pay, Link and 3-D Secure, and keeps the platform out of PCI scope.
• Stripe Customer Portal for invoices and saved payment methods.
• Stripe Tax (optional) for VAT/GST where required — open question, see section 11.
• Coupons and promotion codes managed in admin and synced to Stripe.
7.2 Optional add-ons (phase 2)
• Bundles: e.g. MRCOG Part 1 + Part 2.
• Pause subscription (e.g. up to 2 months) for students whose exam is delayed.
• One-time (non-renewing) passes for students who don't want auto-renew.

10. Non-functional requirements and tech stack
The content is the asset, so protecting it from copying matters as much as speed and uptime.
10.1 Content protection
• Questions load one at a time via authenticated API calls; never a full bank in one response.
• Rate limiting per user (e.g. max questions viewed per hour) with alerts on scraping patterns.
• Text selection and right-click disabled in practice views; dynamic watermark (student email + ID) faintly overlaid on questions and images.
• One active session per account (new login signs out the old one); device limit (e.g. 2 devices) to stop account sharing.
• Images served via signed, expiring URLs.
• No PDF export of paid questions.
10.2 Security and privacy
• HTTPS everywhere, HSTS, OWASP Top 10 protections, secure password hashing, optional 2FA for admins (mandatory for Super Admin).
• Role-based access on every API endpoint; audit log for admin actions.
• PII stripped from uploaded recall sources on ingestion.
• Compliance: Australian Privacy Act, GDPR (UK/EU students), cookie consent banner, data export and deletion on request.
• Daily encrypted backups, 30-day retention, tested restore.
10.3 Performance and reliability
• Page and question loads < 1 s on 4G for the 95th percentile.
• 99.9% uptime target; status monitoring and error tracking (e.g. Sentry).
• Must handle exam-week spikes (assume 10× normal traffic) without degradation.
• CDN for static assets and images.
10.4 Accessibility and devices
• WCAG 2.1 AA.
• Responsive from 360 px phones to large desktops; tested on iOS Safari, Android Chrome, desktop Chrome, Edge, Safari, Firefox.
• Installable as a PWA (home-screen icon) — gives an app-like feel without a native app.
• Dark mode.

13. GoHighLevel (GHL) integration
Recalls Tutor connects to GHL in both directions. Every student signup, trial and purchase is pushed to GHL for marketing and sales follow-up. GHL workflows and funnels can also grant access in Recalls Tutor. Stripe stays the payment source of truth for direct sales.
13.1 Connection
• Connect one or more GHL sub-accounts (locations) from Admin → Integrations, using GHL API v2 (OAuth app or Private Integration token).
• Each connection is set per exam or for all exams, so different exams can feed different sub-accounts or pipelines.
• Partners (section 12) can connect their own GHL sub-account to receive events for their students.
• Tokens stored encrypted; connection health and last sync shown in admin.
13.2 Recalls Tutor → GHL (outbound)

13.3 GHL → Recalls Tutor (inbound)
• GHL workflow "Custom Webhook" action calls the Recalls Tutor API to: grant a QBank plan, start a trial, extend access, or revoke access.
• Uses the same endpoints as the Partner API (section 12.3), under a dedicated internal organisation, so a sale closed by the MEE sales team or a GHL funnel/order form purchase can assign access automatically.
• Option to pass a coupon code from GHL to create a personalised Stripe checkout link that the sales team sends from GHL.
• Idempotency key required, so a re-run workflow never grants access twice.
13.4 Admin settings
• Event toggles: choose which events sync to each connection.
• Field and tag mapping: map Recalls Tutor fields to existing GHL custom fields; edit tag naming patterns.
• Pipeline mapping: which pipeline and stage each event moves the opportunity to.
• Sync log per contact with status, retry button, and automatic retries with backoff when GHL is unavailable.
• Backfill: one-click sync of existing students to a newly connected sub-account.
13.5 Rules
• Marketing consent captured at signup is synced; contacts without consent receive only transactional messages.
• Question content is never sent to GHL — only contact, plan and progress summary data.
• A GHL outage never blocks signup, purchase or practice; events queue and replay.
